# PostgreSQL в Yargram 0.1

Сервер поддерживает PostgreSQL и прежний JSON для совместимости/изолированных тестов. DATABASE_URL автоматически выбирает PostgreSQL; DATABASE_DRIVER=postgres делает выбор явным. При недоступной PostgreSQL сервер сообщает ошибку и не переключается незаметно на пустую JSON-базу.

## Локальный запуск на Windows без Docker

1. Установить зависимости: `npm.cmd install` из корня проекта.
2. В отдельном терминале запустить `npm.cmd run db:local` и оставить его открытым. Если скрипт сообщает `already running`, база уже работает: повторный экземпляр не запускается, можно сразу запускать Yargram.
3. При первом переходе остановить сервер Yargram и выполнить `npm.cmd run db:use-local`.
4. Запустить Yargram обычным способом. После первоначального переноса достаточно «Запустить Yargram.bat»: локальная PostgreSQL автоматически стартует в фоне. Повторять импорт нельзя. Журнал автозапуска — runtime/postgres/launcher.log. Уже работающая база не перезапускается.

Локальный PostgreSQL слушает только 127.0.0.1:55432. Настоящие файлы БД находятся в runtime/postgres/data, случайный пароль — в runtime/postgres/connection.json и database.env (не публиковать). Кластер создаётся в UTF8 для русского текста и эмодзи. Для тестирования используется embedded-postgres; для публичного production рекомендуется отдельная поддерживаемая установка PostgreSQL 16+ или управляемый сервис.

Ctrl+C в окне базы завершает PostgreSQL с сохранением данных. Сначала остановить Yargram, затем базу. После перезагрузки снова выполнить db:local. Удаление runtime/postgres/data удалит локальную базу — сборка этого не делает.

`db:use-local` проверяет локальные порты сервера, делает резервную копию JSON, импортирует только в пустую БД, затем сохраняет резервную копию .env и включает PostgreSQL. Если сервер запущен на другом адресе/порту или другом компьютере, его остановку необходимо обеспечить самостоятельно. При сбое импорта .env не меняется. Повторный импорт в заполненную БД отклоняется.

## Существующий сервер PostgreSQL

Создать отдельного пользователя и пустую базу UTF8. В .env указать:

```dotenv
DATABASE_DRIVER=postgres
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/yargram
```

Пароль в URL должен быть URL-encoded. Для удалённой базы настроить проверяемый TLS согласно провайдеру; не отключать проверку сертификата. Из корня проекта при остановленном Yargram выполнить:

```powershell
npm.cmd run db:import
# Или явно указать источник:
npm.cmd run db:import -- C:/backup/yargram.json
```

Импорт сохраняет ID, хеши паролей, даты, профиль, сообщения, метаданные файлов, заметки, жалобы и звонки. JSON проверяется схемой, копируется в соседний *.backup-* файл и остаётся неизменным. Все вставки выполняются одной транзакцией. Конфликт или заполненная база отменяет импорт. Скрипт не синхронизирует две работающие базы.

DATA_DIR/uploads остаётся хранилищем файлов; при переносе на другой компьютер копировать этот каталог отдельно и задать DATA_DIR. Не менять JWT_SECRET без намерения завершить существующие сессии.

## Устройство хранения

Семь таблиц: users, conversations, messages, attachments, reports, favorite_notes, calls. Каждая сущность — отдельная строка JSONB, а вычисляемые столбцы и индексы обеспечивают поиск, уникальность email/username, выборку переписки и связи. Это не один JSON-документ на весь мессенджер. Операции используют транзакции и блокировки строк; конкурентные изменения проверяются тестами. Целостность связей проверяет прикладной слой; внешние ключи для всех связей JSONB пока не реализованы.

Схема первой версии создаётся при запуске идемпотентно. Для дальнейших изменений структуры потребуется добавить последовательные версионированные миграции. PostgreSQL решает хранение, но не делает несколько backend-процессов полноценным кластером: presence/звонки Socket.IO пока в памяти одного процесса.

## Резервное копирование

Регулярно сохранять `pg_dump -Fc` базы и согласованную копию DATA_DIR/uploads. Для простого согласованного бэкапа остановить запись сервером Yargram, сделать dump и копию uploads, затем возобновить сервер. Проверять восстановление через pg_restore в отдельную пустую БД. Копировать работающий каталог PostgreSQL как обычные файлы нельзя; для физической копии остановить PostgreSQL либо использовать штатные средства резервного копирования.

Старый JSON — снимок момента миграции, после перехода он больше не обновляется. Переключение обратно на JSON не переносит новые сообщения автоматически.

## Проверки

`npm.cmd test` запускает прежние API-тесты, клиентские тесты и тесты на настоящем временном PostgreSQL. Тестовый кластер использует случайный свободный локальный порт и отдельный каталог; рабочая БД не затрагивается. `npm.cmd run smoke` явно выбирает временную JSON-базу и также не изменяет рабочие аккаунты.
