## Ловушка: `Start-Process -RedirectStandardOutput` в PowerShell 5.1

Первый вариант лаунчера перенаправлял вывод копии в файл — журнал остался **пустым**, а ошибки не
было. Причина: в Windows PowerShell 5.1 `-RedirectStandardOutput` падает с «Элемент уже добавлен.
Ключ в словаре: "Path" Добавляемый ключ: 'PATH'», если в окружении есть и `Path`, и `PATH`; ошибка
**не прерывает** вызывающий скрипт, файлы перенаправления создаются, а процесс не стартует. Нашлось
только сравнением вариантов (`Hidden` + redirect / redirect / без redirect) — «нет ошибки» здесь
ничего не значит. Решение: журнал ведёт сам `scripts/backup.mjs` (`--quiet` = только в файл), а
лаунчер запускает без перенаправления. Записано в `memory/arch.md`.

## Второй ящик и поворот отправки (просьба владельца)

Владелец дал второй ящик — `yarikgram@gmail.com` (пароль приложения 16 знаков) — и сформулировал
правило: «первый код отправляется с первого аккаунта который был, и если не получается, то когда
пользователь нажимает на отправить снова, отправляется со второго аккаунта».

Разобрал это на **два разных случая отказа** — их нельзя путать:

1. **Ящик отказал** (пароль, блокировка, сеть). Ошибка видна сразу, поэтому письмо уходит со
   следующего **в том же запросе**: человек получает код как обычно. Если ждать нажатия «отправить
   снова», то при мёртвом основном ящике **каждый** пользователь упрётся в отказ прежде, чем получит
   код, — это хуже, чем то, что уже было.
2. **Ящик письмо принял, а оно не дошло** (спам, потеря). Ошибки нет, сервер узнать не может.
   Единственный сигнал — человек нажал «отправить снова». Ради этого случая повтор идёт **со
   следующего ящика**: иначе повтор пошёл бы тем же путём в ту же «Спам».

Реализация (`services/mail-service.ts`): вместо липкого `preferredIndex` — `lastUsedIndex` (кто
отправил последнее письмо) + `failedUntil` (индекс → до какого времени не выбирать стартовым,
10 минут) + `chooseStart(rotate)`. Обычная отправка стартует с **основного** (`0`), повтор — с
`(lastUsedIndex + 1) % N`. 🔥 Отказавший ящик не выбирается стартовым 10 минут — без этого сломанный
основной стоил бы таймаута на каждом письме; но через 10 минут его снова попробуют (пароль могли
вернуть). Перебор внутри одного вызова остался.

`AuthService.resendCode` → `issueCode(..., { rotate: true })`; регистрация, вход и запрос сброса —
без признака. Признак доезжает до `MailService` через `sendCode({ …, rotate })` → `send(mail, { rotate })`.

Тесты: в `mail-fallback.test.ts` новый блок «поворот ящиков на повторной отправке» (5 тестов: первый
код с основного, повтор со следующего, круг по ящикам, отказавший не стартовый, один ящик не ломается)
+ в `email-code.test.ts` «повторная отправка помечена как повтор, а первая — нет». **Невакуозность
проверена трижды**: поворот выключен → падают 3 теста; пропуск отказавшего убран → 2; `rotate` убран
из `resendCode` → 1.

`.env` — вписаны `MAIL_USER_2`/`MAIL_PASS_2`/`MAIL_FROM_2` (BOM и LF сохранены). Проверено, что сервер
видит ровно два ящика с паролями по 16 знаков. **Настоящую отправку проверить из сессии агента
нельзя** — `smtp.gmail.com` недоступен, nodemailer отдаёт «Greeting never received» на обоих ящиках.
Зато это подтвердило перебор на живых транспортах: попытка в первый, затем во второй, и понятная
ошибка «не сработал ни один из 2». Доставку проверяет владелец кнопкой «Проверить письмо с кодом.bat».

`ИНСТРУКЦИЯ_ПОЧТА.txt` (раздел «ЗАПАСНЫЕ ЯЩИКИ») переписан под два случая; `test-mail.mjs` и
`send-code-mail.mjs` печатают порядок отправки.

## Разбор: хостинг, Cloudflare, «чтобы работало без моего ПК»

Владелец хочет три вещи разом: **работает при выключенном его ПК** + **звонки работают** + **хостинг
бесплатный**. Проверил факты (сайт Raven Host, док-я Cloudflare, `embedded-postgres`, свой код).

**Что уже готово к переезду (проверено в коде):**

- `@embedded-postgres/linux-x64` уже в `package-lock.json`, а `ensure-postgres.mjs`/`local-postgres.mjs`
  кросс-платформенные → **своя база на Linux заведётся**, менять её не надо.
- 🔥 **CORS пропустит любой публичный домен**: `isOriginAllowed` (`http/cors.ts`) считает запрос своим,
  если hostname `Origin` совпал с `request.header("Host")` → туннель работает **без правок `.env`**.
- ✅ **Подписанные ссылки на вложения переносимы**: `/api/uploads/<id>?t=<base64url>.<sig>` строит и
  проверяет **сам сервер** (`lib/media-links.ts`), клиент отдаёт браузеру только путь → смена адреса
  не «осиротит» картинки.
- ⚠️ Нашлось при этом: `siteFrom` (`lib/session-context.ts`) берёт `request.protocol`, а без
  `trust proxy` Express за прокси отдаёт `http` → чужая ссылка в «Активных сеансах» была бы `http://…`.
  **Не исправлено** (лечение — `app.set("trust proxy", true)`).
- ⚠️ `app.ts` держит `upgrade-insecure-requests: null` в CSP **намеренно** (из-за HTTP-адреса) — на
  публичном HTTPS это ослабление, вернуть при переезде.

**Что известно про варианты:**

- **Cloudflare Tunnel** — не требует домена (быстрый туннель даёт `*.trycloudflare.com`), порты наружу
  не нужны, TCP/WebSocket едут. Но **UDP не едет** → WebRTC-звонки по нему не пойдут; ссылка меняется
  при каждом запуске; тело запроса ≤ 100 МБ на бесплатном тарифе (лимит файла у нас 100 МиБ — на границе).
  Требование «работает, когда ПК выключен» он не закрывает: туннель живёт ровно столько, сколько живёт ПК.
- **Бесплатный VPS «навсегда»** с нормальными ресурсами не существует (разбор: только Oracle Cloud
  Always Free, и у него с августа 2026 ARM урезан с 4 OCPU/24 ГБ до 2 OCPU/12 ГБ). Hugging Face Spaces
  с сентября 2026 требует платный план для Docker/Gradio Spaces, а бесплатные Space'ы засыпают.
- Вывод для владельца: бесплатно + без его ПК + звонки = **не сходится**. Либо платный VPS (~€3–4/мес),
  либо его ПК включён, либо звонки отдельным сервером (TURN/SFU в Европе).

## Чек-лист переезда и найденная ошибка зависимостей

## Подробная инструкция под Raven: ещё одна найденная ошибка

Переписал `docs/ИНСТРУКЦИЯ_RAVEN.md` целиком и подробно (части А–Е: свой ПК →
Raven → перенос данных → копии → проверка → обновление).

🔥 **Нашёл ошибку в собственной же первой версии:** написал там
`npm install --omit=dev`, но `npm run build` запускает `tsc` и `vite` — это
**dev-зависимости**, без них сборка невозможна. Правильная последовательность
для shared-хостинга: `npm install --workspaces --include-workspace-root` →
`npm run build` → `npm prune --omit=dev` (вернуть место на диске).

🔥 **Вторая находка: `dist/` в `.gitignore`** (проверено `git check-ignore`:
`.gitignore:5:dist/` и `apps/web/.gitignore:2:dist`). Значит собранные файлы
через git на сервер **не уезжают** — сборку надо делать на сервере, а при
обновлении кода `npm run build` там же обязателен. Запасной путь (архив через
File Manager) тем и ценен, что `dist` можно загрузить вручную.

Также уточнил: `DATA_DIR` по умолчанию = `apps/server/data` (из `config.ts`:
`dataFile = resolve(DATA_DIR, "yargram.json")`), задавать не обязательно;
`PORT` читается из env (по умолчанию 3000) и должен совпасть с портом,
который выделила панель.
