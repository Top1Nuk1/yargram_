## 🔥 Грабли: pg-пул без обработчика 'error' роняет процесс

Первая же проверка на GitHub упала, хотя **все тесты прошли** (12 + 47 + 4
файла). `##[error]Process completed with exit code 1` — потому что vitest
считает прогон провальным при «Unhandled Errors»: было **6 необработанных
исключений** из `tests/postgres.test.ts`, все — `FATAL 57P01 terminating
connection due to administrator command`.

Причина: `PostgresDatabase` создавал `new Pool(...)` **без обработчика
`'error'`**. `pg-pool` на ошибку клиента, простаивающего в пуле, делает
`pool.emit('error', err, client)` (`node_modules/pg-pool/index.js`,
`makeIdleListener`), а необработанное событие `'error'` в Node **роняет
процесс**. В тестах это происходит, когда `cluster.stop()` гасит встроенную
базу, пока соединения ещё висят. Локально на Windows не воспроизводится
(там база гаснет иначе) — поэтому баг жил незамеченным.

⚠️ Это **не только про тесты**: в бою перезапуск/перезагрузка PostgreSQL под
работающим сервером Yargram убила бы процесс целиком.

Починено: в конструкторе `this.pool.on("error", …)` — пишем в журнал и живём
дальше (следующий запрос возьмёт живое соединение). Сторож —
`apps/server/tests/pool-errors.test.ts` (`pool.emit('error', …)` не должен
бросать).

⚠️ **Мораль на будущее:** `npm run verify` и прочие прогоны через `| tail`
**теряют код возврата** (возвращается код `tail`). Проверять надо
`cmd > log 2>&1; echo $?` — иначе «всё зелёное» окажется ложью.

Итог: коммит `7219a8d` залит, проверка на GitHub — **`completed success`**

## Баннеры не прогружались вовсе

Жалоба: «баннера не прогружаются никак, даже те, которые загрузили».

**Причина — разводка двух сайтов.** Встроенные картинки Yargram (баннеры
профиля, обои, фоны) адресуются **от корня** — `/banners/Yargram-banner-blue.png`,
`/wallpapers/…`, `/backdrops/…` — и ровно такой строкой лежат в профиле человека
(`bannerUrl`). Но корень занят **лендингом**, а приложение живёт на `/app`.
Своих картинок у лендинга нет, и запрос проваливался в одиночный маршрут
`app.get("*")`, который отдавал `index.html` **со статусом 200**.

Почему это было незаметно: браузер просит картинку с
`Accept: image/avif,image/webp,image/*,*/*;q=0.8`, и `*/*` делает HTML-страницу
«приемлемым» ответом. То есть `request.accepts("html")` для картинки **истинно**
→ `sendFile(webIndex)` → `<img>` получает HTML вместо PNG и молча не рисует
ничего. Существующий тест «не-HTML запрос к корню не отдаёт страницу» ставил
`Accept: image/png` **без `*/*`** — и проходил, хотя в браузере всё было сломано.

Проверка живого сервера (`curl -H "Accept: image/…,*/*"`):
`/banners/…` → `200 text/html` (2323 байта, это `index.html` лендинга),
`/app/banners/…` → `200 image/png`. **Загруженные** баннеры при этом работали:
`/api/uploads/…` отдаёт настоящие байты (проверено по сигнатурам — GIF/PNG/JPEG).

Починено в `apps/server/src/app.ts`: в продакшене папки `banners`, `wallpapers`,
`backdrops` из `webDistPath` отдаются **от корня явно**, а следом за статикой
стоит обработчик, который на отсутствующий файл отвечает `404 ASSET_NOT_FOUND` —
чтобы браузер больше никогда не получал HTML под видом картинки.
Сторож — тест «встроенные картинки Yargram отдаются с корня картинкой, а не
страницей» с **настоящим** заголовком браузера.

⚠️ Рядом замечено и **не тронуто** (не относится к жалобе): в `app.ts` в

## Бот поддержки: «Бот поддержки не настроен»

Две причины, обе настоящие.

**1. Аккаунта бота не было в базе.** `node scripts/create-support-bot.mjs`
заводит `@YargramSupport_Bot` (`isBot`, `isApp`, значок Yargram, галочка,
`isOwner`) и служебную группу `isSupportInbox`. Без него
`SupportBotService.requireBot()` бросает `503 SUPPORT_BOT_MISSING`.

**2. 🔥 Вторая группа в базе не могла появиться вообще.** `conversations_direct_key_unique`
был **общим** уникальным индексом по `direct_key`, а у всех групп `directKey` —
пустая строка (у личных диалогов там `id1:id2`, у «Избранного» — `saved:<id>`).
Значит, **вторая** группа в базе падала с `duplicate key value violates unique
constraint "conversations_direct_key_unique"` — то есть не работало не только
создание служебной группы, но и **создание групп людьми**. В базе была ровно
одна группа («Админ группа»), что это и подтверждало.

Починено:
* индекс стал **частичным**: `... ON conversations (direct_key) WHERE direct_key <> ''`
  — как соседний `conversations_invite_code_unique`;
* старый индекс приходится сносить: `CREATE ... IF NOT EXISTS` определение
  существующего индекса **не меняет**. В `postgresSchemaSql` добавлен `DO $$`
  блок, который убирает индекс без `WHERE` и пересоздаёт его с условием — на
  каждом запуске сносить не нужно;
* в `findOrCreateSaved`/`findOrCreateDirect` в `ON CONFLICT (direct_key)`
  добавлено `WHERE direct_key <> ''`: без повтора условия Postgres **не выведет
  частичный индекс** по цели конфликта и запрос упадёт.
* 🔥 Грабли при правке: `postgresSchemaSql` — это **шаблонная строка**, и
  обратные кавычки в SQL-комментарии её закрывают (TS начинал разбирать SQL как
  код). В комментариях внутри неё — только обычные кавычки.
* Сторож — тест «lets a second group exist: the direct key index skips empty keys».

Живую базу поправил на месте (`DROP INDEX` + `CREATE UNIQUE INDEX ... WHERE
direct_key <> ''`), затем `node scripts/create-support-bot.mjs` прошёл:
бот `b1e7d0a2-3548-4785-98c2-507f82bd440c`, группа `Yargram · Поддержка`
`8f8d5994-ff98-4d45-9d1a-fe485a7d1a2f`, в ней владельцы `Top1Nuk1` и `#인간 앎`.

⚠️ Бот работает **без перезапуска** (`requireBot()` ищет аккаунт в базе на каждом
