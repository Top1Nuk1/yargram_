### Две ловушки, на которые наступил

1. **Почему сеансы «слипались»:** одинаковые JWT. Токены подписывались только по `sub` + времени
   с точностью до секунды, а два входа подряд попадают в одну секунду → побайтово одинаковые
   токены → все входы выглядят как один сеанс, «новый вход» не показывается. Лечится `jwtid`
   (`randomUUID()` в `SignOptions`). Тесты от этого падали пачкой.
2. **Почему `sessionAutoTerminateDays` не сохранялся:** поля не было в `userSchema`
   (`storage/json-database.ts`) — хранилище молча вырезало его при чтении. Классическая грабля
   проекта: новое поле `User` надо вписывать и в Zod-схему, и в `update` обоих репозиториев.
   Заодно `toCurrentUser` теперь отдаёт поле **всегда** (`?? null`), а не только когда оно есть.

## Сводка в админ-панели: сколько всего аккаунтов и групп

Просьба: «в админ панели можно было посмотреть сколько всего групп в Yargram,
сколько аккаунтов».

- **Считает сервер, а не клиент.** Руками по спискам этого не узнать: `GET /users` — поиск по
  подстроке с жёстким пределом выдачи (`list` делает `.slice(0, limit)`), а `GET /admin/groups`
  отдаёт только первые совпадения. Поэтому добавлены `UserRepository.count()` и
  `ConversationRepository.countGroups()` в оба репозитория: JSON — длина массива / фильтр по
  `type === "group"`; Postgres — `SELECT count(*)::text FROM users` и
  `... WHERE payload->>'type' = 'group'` (счётчик берём у базы, не тянем записи в память).
- `AdminService.stats(grantorId)` → `{ totalUsers, groups }`, только владелец (иначе 403
  `NOT_OWNER`); два счётчика считаются через `Promise.all`. Ручка `GET /api/admin/stats`
  отдаёт `{ stats }`.
- 🔥 **Аккаунты считаются вместе с удалёнными и замороженными** — удаление мягкое, запись
  остаётся в базе и держит почту с ником занятыми. Это закрыто тестом: после
  `DELETE /api/admin/:id` число не меняется.
- **Группы — только `type === "group"`**: личные диалоги и «Избранное» в счёт не идут.
- Клиент: плитки «Аккаунтов» / «Групп» в `AdminPanel.tsx` (компонент `SummaryTile`, иконки
  `UserRoundCheck` / `UsersRound`), новый тип `AdminStats`, метод `api.adminStats()`.
  Счётчики читаются при открытии панели; **сбой сводки не ломает панель** — своя строка
  `admin.statsFailed`, поиск и знаки работают дальше. Ключи `admin.overview`,
  `admin.accountsTotal`, `admin.groupsTotal`, `admin.overviewHint`, `admin.statsFailed`
  на ru/en/bg/uk/be.
- 🪤 **Грабля в тесте:** `POST /api/conversations/saved`, а не `GET` — я написал GET и получил
  404. Название есть в `docs/API.md` как отдельная строка, но метод надо смотреть в `routes.ts`.
- Тест невакуозный: правка `api.adminStats(token)` → `adminStatsNeutered(token)` валит все 9
  тестов `AdminPanel.test.tsx`.

## Отбор в списке аккаунтов: три слоя (состояние / знаки / область поиска)

Просьба: «добавить фильтр по галочка, значок yargram, scam, fake, удалённый, замороженный,
не удалённый и не замороженный; ещё поиск чтобы по юзам можно искать или по нику или всё сразу».

- Отбор разделён на **три независимых слоя**, а не на один комбинаторный список:
  • `filter` — состояние (`all|active|frozen|deleted`), уже было;
  • `marks` — знаки, **мультивыбор**, складываются по И (`marks.every(...)`):
    `verified|badge|scam|fake|owner`. `badge` — это ровно `badge === "yargram"`, `owner` —
    `isOwner === true`. Неизвестные значения отбрасываются в Zod-трансформации, а не падают.
  • `scope` — где искать `q` (`any|name|handle`): `name` → только `displayName`,
    `handle` → только юзернеймы (основной + дополнительные), `any` → имя + юзернеймы + почта.
- 🔥 **«Замороженный» ≠ «удалённый»**: удалённый аккаунт может иметь `isFrozen`, но в фильтр
  `frozen` не попадает (иначе «разморозить» его было бы нельзя). `active` — ни удалён, ни заморожен;
  это и есть «не удалённый и не замороженный» из просьбы (в UI — кнопка «Активные»).
- Server: `AdminService.listAccounts(grantorId, { query, filter, marks, scope })` + хелперы
  `matchesState` / `matchesMarks` / `matchesQuery`; Zod-схема `adminAccountsQuerySchema`
  принимает `marks` как строку через запятую (`.transform` → массив).
- Client: `FilterGroup` + `FilterChip` (`aria-pressed`), состояние `accountMarks: AdminAccountsMark[]`,
  `accountScope`; чипы области поиска **погашены, пока строка пуста** (`disabled={!search.trim()}`),
  кнопка «Сбросить фильтры» (`admin.filtersReset`) видна, только если отбор тронут.
  Новые ключи i18n (`filterStateLabel` / `filterMarksLabel` / `filterScopeLabel`, `mark*`, `scope*`)
  на ru/en/bg/uk/be.
- Тесты (клиент, 20 в `AdminPanel.test.tsx`): «складывает знаки и состояние в один отбор»
  (проверяет `['verified','scam','owner']`), «выбирает, где искать введённое», «сбрасывает весь
  отбор одной кнопкой», «гасит выбор области поиска, пока строка пуста».

## «Заходил когда» в списке аккаунтов

Просьба: «Добавь ещё когда в последний раз заходили».

- 🔥 **Пришлось чинить старую логику, а не только добавлять поле.** В `userSchema`
  (`storage/json-database.ts`) в `.transform` стояло
  `lastSeenAt: user.showLastSeen === false ? null : user.lastSeenAt` — это **клиентское** правило
  приватности, вшитое в хранилище: оно **стирало время входа у всех, кто скрыл его от других**,
  причём на уровне чтения из БД. Из-за этого у скрывших аккаунтов время было бы навсегда потеряно,
  и в админке они выглядели бы так же, как брошенные. Правило перенесено в `toPublicUser`
  (`domain/models.ts`, строка про `lastSeenAt`/`lastSeenStatus`) — там ему и место; хранилище теперь
  хранит истину: `lastSeenAt: user.lastSeenAt ?? user.createdAt`.
  Симптом: в админке у аккаунта с `showLastSeen: false` `lastSeenAt` был бы `null`.
- `AdminAccountView.lastSeenAt: string` (**не** `string | null`) + проброс в `toAdminAccountView`.
  Отдаём **истинное** время входа: настройка приватности касается посторонних, админке нужен факт
  входа, иначе не отличить брошенный аккаунт от живого. Падение на `createdAt` гарантирует, что
  поле никогда не пусто, — у старых записей без поля дата создания.
- **Время обновляется при каждом обращении к API** (middleware `updateLastSeen`, `auth-service.ts`),
  а не только при входе: «заходил» означает реальную активность.
- Клиент: `AdminAccount.lastSeenAt`, строка дат в `AccountRow` стала
  «создан … · заходил … [· удалён …] [· заморожен]», ключ `admin.lastSeenAt` на ru/en/bg/uk/be.
- Тесты: серверный — `lastSeenAt` строкой и непустой у всех + 🔥 проверка, что при
  `showLastSeen: false` владелец **всё равно** видит истинное время (сверяется с записью в
  хранилище); клиентский — «заходил 5 января 2026» у живого и «заходил 1 января 2026» (= дата
  создания) у удалённого. Невакуозность проверена: подмена ключа `admin.lastSeenAt` на
  несуществующий валит 1 тест.

Проверено: `npm run verify` (сервер 107, клиент 324), `npm run build`. Документация: `docs/API.md`
(абзац про `lastSeenAt` под `/admin/accounts`), `Функции Yargram.txt` (админ-панель).

## Стрелка «назад» в разделах настроек

Просьба: стрелка на экранах «Язык» / «Конфиденциальность» / «Активные сеансы» должна возвращать
**на прошлый экран** (список настроек), а не выбрасывать в переписку.
Причина: `SettingsScreen` при открытии раздела закрывает себя (`setSettingsOpen(false)`), а
`onClose` раздела делал только `setXOpen(false)` — возврат вёл «в никуда».
Решение: необязательный проп **`onBack?: () => void`** у трёх экранов; стрелка и `Escape` зовут
`onBack ?? onClose`, крестик («Закрыть») всегда `onClose`. В `MessengerScreen` `onBack` =
`setXOpen(false) + setSettingsOpen(true)`. Без пропа поведение прежнее (можно открыть в одиночку).
